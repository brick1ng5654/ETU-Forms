# Security Policy (SECURITY.md)

Документ описывает текущие меры безопасности в проекте (backend API, аутентификация, хранение паролей, rate limiting, логирование), а также правила управления секретами и рекомендации для продакшн-развёртывания.

> Важно: этот документ отражает текущие договорённости и реализацию. Любые изменения в механизмах аутентификации/хранения секретов должны сопровождаться обновлением SECURITY.md.

---

## 1) Scope и модель угроз

### Что защищаем
- Учётные записи пользователей (вход через email+пароль для “ЛК партнёра”).
- Доступ к API и данным форм.
- Пароли (в виде хэшей), JWT-токены, секреты окружения.
- Доступность `/auth/login` (защита от перебора и DoS на уровне приложения).

### Базовые угрозы
- Перебор паролей (brute-force).
- Credential stuffing.
- Утечка базы данных (нападающий получает `password_hash`).
- Подмена IP через `X-Forwarded-For` при неправильной настройке прокси.
- Логирование секретов (пароль/токен в логах).
- Нагрузка/DoS на `/auth/login` через массовые запросы.

---

## 2) Аутентификация: вход через email+пароль

### Регистрация
Самостоятельная регистрация **отсутствует**. Пользователи создаются администратором/сервисом.

### Поведение ошибок
- При неверных данных входа возвращается **одинаковая** ошибка:
  - `401 Invalid email or password`
- Это снижает риск user enumeration (определение существования email).

## 3) Хранение паролей

### Алгоритм хэширования
Используется **Argon2id**.

Реализация: `app/security/passwords.py`.

Пример конфигурации хэшера (зафиксировано в коде):
- `type=argon2id`
- `time_cost=3`
- `memory_cost=65536` (64 MiB)
- `parallelism=1`
- `hash_len=32`
- `salt_len=16`

> Salt хранить отдельно в таблице **не нужно**: Argon2 (через `argon2-cffi`) сам генерирует соль и включает её в строковый хэш.

### Pepper (секрет приложения)
Дополнительно применяется **pepper**: к паролю дописывается секрет из окружения перед хэшированием.

- Pepper хранится **только** в окружении (env/secret manager), не в БД.
- Переменная: `PASSWORD_PEPPER`
- При отсутствии `PASSWORD_PEPPER` приложение должно падать/не запускаться корректно (fail fast), либо логин недоступен.

### Ограничение длины пароля
Чтобы не хэшировать мегабайтный ввод (DoS на CPU/RAM):
- Валидация в Pydantic (`schemas.py`) ограничивает `max_length`.
- Дополнительно проверка в `hash_password()` (на случай обхода схемы).

Рекомендуемые параметры:
- `min_length`: 8
- `max_length`: 128 (или 256 максимум, но лучше 128)

### Нормализация email
Перед проверкой/поиском пользователя email нормализуется:
- `email = email.strip().lower()`

Это устраняет расхождения `Admin@Example.com` vs `admin@example.com`.

## 4) JWT токены доступа

Используются JWT access token для сессии.

Реализация: `app/security/tokens.py`.

### Параметры
- Алгоритм: `HS256` (симметричный ключ).
- Секрет подписи: `SECRET_KEY` (строго из env).
- Время жизни: на текущем этапе фиксировано (например 60 минут).

### Рекомендации
- При компрометации — **немедленная ротация** `SECRET_KEY` (все токены станут невалидными).

## 5) Rate limiting для /auth/login

Цель: защита от перебора пароля и перегрузки.

Реализация: `app/security/rate_limiter.py` и использование в `app/api/v1/endpoints/auth.py`.

### Правила (key space)
Ограничение применяется по двум ключам:

1) Глобально по IP:
- `login:ip:{ip}`
- Снижает DoS с одного IP.

2) По IP + email:
- `login:ip_email:{ip}:{email}`
- Снижает brute-force на конкретный аккаунт с одного IP.

### Важно
- Rate limiter должен вызываться **до** проверки пароля и до тяжёлых операций.
- Ответ при блокировке:
  - `429 Too Many Requests`
  - Заголовок `Retry-After: <секунды>`

## 6) Логирование событий безопасности

### Логирование неудачных попыток входа
Реализация: `app/security/auth_logging.py`.

Логируется событие `auth_login_failed` со следующими полями:
- `email` (нормализованный)
- `ip`
- `user_agent`
- `reason` (например `invalid_credentials`, `rate_limit_ip`, `rate_limit_ip_email`, `no_password_set`)

### Что НЕ логируем
Никогда не пишем в логи:
- пароль (в любом виде)
- JWT токены
- password_hash
- pepper / SECRET_KEY
- любые секреты окружения

### Зачем это нужно
- аудит попыток перебора
- быстрый поиск атак по IP/email
- мониторинг аномальной активности

## 7) Администратор (seed)

Проект содержит механизм создания admin пользователя при старте (seed).

Реализация: `seed_admin()` (используется в `lifespan` в `app/main.py`).

### Требования
- Admin создаётся только если отсутствует.
- Пароль admin **должен быть изменён** при первом использовании.

> Если сейчас пароль задан фиксированно для разработки — обязательно отметить это как dev-only и запретить в prod.

---

## 8) Reverse proxy и real IP

- `X-Forwarded-For` можно использовать **только если доверяем прокси**.
- Нельзя доверять XFF от клиента напрямую (его легко подделать).

### Рекомендации для prod
- Ограничить доступ к backend напрямую (только через прокси).
- На прокси настроить корректную передачу real IP.
- В приложении учитывать XFF только от доверенного прокси/сети.

---

## 9) Управление секретами (ENV)

### Обязательные переменные окружения
| Переменная | Назначение | Где хранить |
|---|---|---|
| `PASSWORD_PEPPER` | pepper для паролей | secret manager / CI secrets |
| `SECRET_KEY` | подпись JWT | secret manager / CI secrets |
| `POSTGRES_*` | доступ к БД | env/secret manager |
| `ADMIN_*` | сид админа | только secrets |
